# Backlog للـ Backend — Academy Learning Platform

تاريخ المراجعة: 19 أكتوبر 2026.

هذه خطة عمل محلية قابلة للنقل إلى Jira؛ لم يتم إنشاء issues داخل Jira.
المعرّفات مثل FND-01 للتخطيط والربط هنا وليست مفاتيح issues حقيقية.

## النطاق والقرارات

- منصة SaaS لأكاديميات مدرّسي المناهج. صاحب الأكاديمية يدفع اشتراك البرنامج.
- الطالب يمكن أن ينضم ويشتري كورسًا؛ حساب المستخدم واحد وعضوياته متعددة.
- الأكاديمية هي الجهة البائعة. حساب التحصيل والمستفيد الفعلي يجب تثبيتهما مع
  مزوّد الدفع؛ لا يُستنتجان من المدرس المكلّف بالكورس.
- الكورسات منظمة بالمادة والصف والسنة والترم، وتشمل دروسًا وموارد وامتحانات.
- النمط المتفق عليه: CQRS مع orchestrators عند الحاجة، وتجميع ملفات Academies
  في Commands وValidation وOrchestrators وDTOs وViewModels وQueries وControllers.
- المعاملة يديرها executor مشترك يدعم التداخل بـ depth ويمنع الحفظ بعد فشل داخلي.
- هذه الخطة للـ Backend الموجود في المستودع. واجهات الطالب والمدرس والإدارة
  تحتاج backlog منفصلًا حسب التصميم والتقنية المختارة، وليست ضمن تقديرات هذه الخطة.
- خارج أول إصدار: Marketplace عام، سلة عبر أكاديميات متعددة، محافظ وتقسيم أرباح،
  بنك أسئلة مشترك، تطبيقات موبايل، بث مباشر، وأولياء أمور. إضافتها تحتاج قرار نطاق.

## الحالة الفعلية عند المراجعة

| الجزء | الحالة |
|---|---|
| هيكل فولدرات المشروع وتقسيمة Academies | مجهّز؛ يُراجع عند نقل الخطة إلى Jira |
| تجهيز قاعدة بيانات التطوير والاتصال الفعلي | غير مكتمل حسب تأكيد صاحب المشروع؛ FND-00 أول مهمة تجهيز |
| IGenericRepository | interface فارغة |
| IUnitOfWork | كلاس فارغ يحتاج تصحيح النوع والعقد |
| RequestResponse وEndpointRespone | كلاسات فارغة؛ Result pattern لم يُنفّذ بعد |
| Domain/Entities وDomain/Enums | مجلدات بدون ملفات تنفيذ حاليًا |
| DbContext وEF mappings وtransaction executor | غير موجودة في المصدر الحالي |
| Commands وhandlers وcontrollers للـ features | غير منفذة |
| المصادقة والدفع والامتحانات | غير منفذة |
| الاختبارات | لا توجد ملفات مصدر اختبارات حاليًا |

وجود فولدر أو نجاح بناء القالب ليس دليلًا على اكتمال feature. لا تُعلّم مهام
الـ entities أو الامتحانات Done استنادًا إلى محادثة سابقة؛ راجع المصدر الحالي.

## طريقة إدخال المهام إلى Jira

أنشئ Epic لكل مجموعة أدناه. مهام التأسيس والبنية تكون Task، والوظائف التي
يستخدمها صاحب الأكاديمية أو الطالب يمكن تسجيلها Story. سجّل الاعتماديات كـ
is blocked by. الأولويات هنا P0 = مانع للوظائف الأساسية، وP1 = لازم للنسخة
التجريبية الكاملة؛ لا توجد مدد أو story points قبل تحديد السعة وتقدير الفريق.

كل عملية عمل تملك Command/Query وhandler وvalidation وDTO/ViewModel وcontroller
action أو endpoint حسب الحاجة، مع التوثيق والاختبارات المناسبة. هذه ليست
issues مستقلة لكل طبقة؛ يمكن تحويلها إلى subtasks داخل العملية إن احتاج الفريق.

## E01 — Foundation and persistence

### FND-00 — Set up development SQL Server and verify database connectivity

- النوع: Task. الأولوية: P0. يعتمد على: لا شيء.
- الوصف: تجهيز محرك SQL Server المناسب لبيئة التطوير، وإنشاء قاعدة مخصصة
  للمشروع وإعداد الاتصال بها. تحديد وسيلة التشغيل حسب البيئة المتاحة
  (SQL Server أو LocalDB أو container)، بدون افتراض أن السيرفر مثبت أو جاهز.
- القبول: اختيار instance واسم قاعدة واضحين؛ قاعدة التطوير منفصلة عن الاختبار
  والإنتاج؛ اختبار اتصال فعلي وأذونات الحساب المطلوبة؛ بيانات الاتصال الحساسة
  في User Secrets أو environment variables خارج المستودع؛ توثيق التشغيل والاتصال
  وحل مشاكل الشهادة/الاتصال في بيئة التطوير. لا تعتمد المهمة على وجود entities
  أو تنفيذ feature، ولا تُنفّذ migrations تلقائيًا على قاعدة موجودة ببيانات.
- المهام الفرعية المقترحة: تجهيز instance، إنشاء قاعدة التطوير، إعداد الاتصال
  وأسراره، اختبار الاتصال وتوثيقه.

### FND-01 — Implement application results and HTTP responses

- النوع: Task. الأولوية: P0. يعتمد على: لا شيء.
- الوصف: تنفيذ Result للـ handlers، ونتيجة الاستجابة للـ endpoints، وأخطاء بأنواع
  وأكواد ثابتة. تصحيح الأسماء الحالية قبل الاستخدام.
- القبول: نجاح بقيمة ونجاح بدون قيمة وفشل؛ لا توجد نتيجة نجاح تحمل خطأ؛ mapping
  واضح إلى 400/401/403/404/409/500 حسب الحالة؛ أخطاء الحقول المتعددة مدعومة؛
  تفاصيل الاستثناءات الداخلية لا تظهر في HTTP responses؛ اختبارات للحالات.

### FND-02 — Implement academy membership domain and SQL Server context

- النوع: Task. الأولوية: P0. يعتمد على: FND-00.
- الوصف: ApplicationUser وAcademy وMembership وmembership roles، وبروفايلات
  Student وInstructor اللازمة؛ توثيق العلاقات والمفاتيح ومراجعتها، ثم تنفيذ
  Identity وDbContext وmappings وأول migration على قاعدة التطوير الجاهزة.
- القبول: المستخدم ينضم لأكاديميتين بأدوار مستقلة؛ لا تتكرر العضوية لنفس الجهة؛
  يمكن تعدد الأدوار داخل العضوية؛ لا يتجاوز عدد الملاك الأساسيين واحدًا؛
  علاقات البروفايل لا تقبل عضوية جهة أخرى؛ تحديث قاعدة تطوير فارغة بنجاح،
  وإمكانية بناء المخطط من migrations على قاعدة اختبار جديدة؛ بيانات بداية
  غير حساسة عند الحاجة وبطريقة لا تكرر السجلات؛ لا تُطبّق على بيانات فعلية
  دون خطة ترحيل. مخططات الكورسات والامتحانات والمبيعات تضاف مع مهامها تدريجيًا.

### FND-03 — Implement persistence contracts and unit of work

- النوع: Task. الأولوية: P0. يعتمد على: FND-02.
- الوصف: تصحيح IUnitOfWork، وتنفيذ الوصول للبيانات اللازم فقط والعقود الحالية
  حسب الاستخدام، مع تسجيل الخدمات في DI.
- القبول: DbContext مشترك داخل scope؛ المستودع لا يحفظ تلقائيًا؛ دعم cancellation؛
  عدم تسمية IQueryable بـ Async؛ القراءة تستطيع projection وpagination؛
  لا تُفرض abstractions أو repositories مكررة لكل entity بلا احتياج.

### FND-04 — Implement nested transaction execution

- النوع: Task. الأولوية: P0. يعتمد على: FND-01، FND-03.
- الوصف: ExecuteAsync مشترك مع depth، يستخدمه orchestrator داخل آخر على نفس
  DbContext. تحديد هل الفشل يُعبّر عنه بـ Result أو exception في العقد.
- القبول: الخارجي فقط يفتح المعاملة ويحفظ ويعمل commit؛ فشل داخلي بـ Result
  أو exception يمنع commit حتى لو تم التقاطه؛ rollback والتنظيف والتعامل مع
  cancellation؛ depth يعود صحيحًا في finally؛ النتيجة التي تعتمد على ID مولّد
  تُجهّز بعد الحفظ؛ اختبار استدعاء متداخل ناجح وآخر يفشل واختبار exception ممسوك.
  إذا فُعّلت retries لمزوّد SQL Server، تندمج مع حدود المعاملة بصورة صحيحة.

### FND-05 — Implement request validation and consistent error handling

- النوع: Task. الأولوية: P0. يعتمد على: FND-01.
- الوصف: تشغيل validators، وتوحيد استجابة الاستثناءات والأخطاء المتوقعة وتسجيلها.
- القبول: طلب غير صالح لا يدخل الكتابة؛ أخطاء 400 بتفاصيل الحقول؛ 500 آمنة
  ومعرّف تتبع في logs؛ لا يتم تسجيل passwords أو tokens أو مفاتيح الدفع؛
  قواعد validation لا تنفّذ مرتين نتيجة controller وpipeline معًا.

### FND-06 — Establish automated tests and build checks

- النوع: Task. الأولوية: P0. يعتمد على: FND-02.
- الوصف: مشروع اختبارات، fixture لقاعدة اختبار معزولة، وbuild/test في CI.
- القبول: اختبارات لا تتصل بقاعدة التطبيق؛ تحقق العلاقات الحرجة على مزوّد
  SQL Server قبل الإصدار؛ CI يفشل عند فشل build/tests؛ الاختبارات اللازمة
  لكل task تُضاف معها، وليس فقط في نهاية المشروع.

## Definition of Done لكل task

- معايير القبول الخاصة بالمهمة متحققة، والكود build ناجح.
- validation والصلاحيات ونطاق الأكاديمية متحققون على الخادم عند انطباقهم.
- unit/integration tests للسلوك الحرج، والفشل والتكرار والتزامن بحسب المخاطر.
- استجابات موحدة وعقد API وأمثلة طلبات محدثة، بدون مفاتيح إجابات أو أسرار مكشوفة.
- تغييرات الموديل معها migration قابلة للمراجعة واختبار على قاعدة منفصلة.
- لا حفظ متفرق يكسر حدود المعاملة، ولا افتراض rollback للبوابات أو التخزين الخارجي.
- حالة Done مبنية على كود واختبار قابلين للتشغيل؛ وجود الملف أو الفولدر لا يكفي.

لو مهمة أكبر من قدرة الفريق على إتمامها واختبارها داخل الدورة، تُقسّم إلى
عمليات مستقلة قابلة للمراجعة، مثل DraftExam وPublishExam، مع الحفاظ على معايير
القبول والاعتماديات. لا تُسجل مواعيد أو تقديرات أو assignees افتراضية.
